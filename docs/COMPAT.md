# 互換の方針（データを壊さない約束）

1.0.0 以降（1.x）で、利用者のデータを壊さないための約束と、その守り方をまとめた文書です。
Issue #84 の方針を文書にしたもので、保存形式を変える変更（PR）は、この文書の手順に従います。

- この文書は 0.9.1 の時点（次の 0.10.0 は未リリース）の内容です。**約束のうち、今はまだ満たせていないもの**は「[5. 既知の穴と要確認](#5-既知の穴と要確認)」に分けて書いています（隠さずに、テストでも追跡しています）。
- 仕様の細部は [SPEC.md](SPEC.md) の 8 章（保存）・付録 B（ファイル形式）・付録 E（`check-jira`）、版ごとの変更は [CHANGELOG.md](CHANGELOG.md) の「互換」の節にあります。
- 版ごとの見本とテストは `tests/compat/` と `tests/unit/test_compat.cpp` です。

| 5 | **新しいキーは、既存の意味を変えず、読み飛ばせる形で足す**（4 章） | 方針 |

| 場所 | 残る？ | 備考 |
|---|---|---|

| `ui` の中（`ui.cols` の中も） | **残る** | `ui` は JSON のまま持つ |

「消える」場所があるので、**当面は、新しい情報を `project.settings.json` のトップレベルの新しいキー（か `ui`）に足す**ことにします（4 章）。既存の項目の中にキーを足すのは、その項目が未知のキーを保つようになるまで避けます。

## 3. 壊す変更と、やむを得ない場合の手順

**壊す変更**（1.x では入れない）:
- 古いデータが読めなくなる、または読んで別の意味になる。
- 既存のキー・列の意味・型・単位・書式を変える。
- 既存のキー・列を消す、名前を変える。
- 保存し直すと、古い版が読めなくなる形に書き換える。
- 日程の計算結果（golden）が変わる。golden は正解データなので、更新するときは必ず利用者に確認する（CLAUDE.md）。

**やむを得ない場合**（1.x の中でどうしても必要なとき）は、次をすべて満たします。0.4.0 の「平置き → フォルダ構成」の移行が手本です（SPEC 8.8）。
1. **自動では動かさない**。通知とボタンで知らせ、利用者が選んだときに移す。移さなくても今までの形で読み書きできる。
2. **先に全部を控える**。移す前に、触るファイルをすべて控えの場所へ写す（0.4.0 は `_バックアップ/移行前.<日時>/`）。1 つでも控えに失敗したら何も動かさない。`バックアップ/` には今は CSV しか控えないので、**設定のファイルも控える**。
3. **バイト列を保って写し、読み戻して一致を確かめてから**、古い形を消す。失敗したら古い形を残し、通知に出す。
4. **移行前の見本を `tests/compat/` に残し**、移行のテストを書く（バイト列・未知のキー・失敗時に元が残ること）。
5. CHANGELOG の「互換（更新する前に）」に、戻せないこと（古い版では開けない場合）と、戻す手順を書く。

## 4. 新しいキーの足し方

保存形式に何かを足すときは、次を守ります。

1. **既存のキー・列の意味を変えない**。型も単位も書式も変えない。
2. **読み飛ばせる形にする**。古い版が知らなくても、無視して（か、そのまま保って）安全に動くこと。読む側は、欠けていたら既定値で動き、壊れた値は項目単位で読み飛ばす（`attachments`・`links`・`baselines` などと同じ流儀）。
3. **足す場所は、いまのところ `project.settings.json` のトップレベルの新しいキーか `ui` の中**（2 章の表）。既存の項目の中に足すときは、先にその項目が未知のキーを保つようにする。
4. **空・既定のときは書かない**（`attachments` などは空なら書かない）。その機能を使っていない利用者のファイルを変えない。
5. **CSV に足すのは、末尾の未知の列として**。JIRA の標準の列名と衝突させない。値が 1 件もないときは列を作らない（`Resolved`・`Created`/`Updated` と同じ）。取り込み → 書き出しだけでは増やさない。
6. **共有・バックアップ JSON には、環境依存のもの（パス・URL）や個人情報を入れない**（`links`・`baselines`・`history`・`weekly`・`weeklyAuto` は入れていない）。
7. 上限と検証を決める（件数・長さ・Issue Id は `isSafePathComponent`）。

## 5. 既知の穴と要確認

約束を満たしていない点と、確かめられていない点です。1.0.0 の前に直すか、方針を決めます。

**穴（テストで追跡している）**
1. **未知のキーが消える場所がある**（2 章の表）。`res`・`attachments` の項目・`weekly` の直下・`baselines`・`history` の中と、prefs の入れ子。`test_compat.cpp` の `should_fail` のテストが、直ったとき（＝テストが「失敗しなくなった」とき）に知らせる。直し方の案: 各項目の型に `extra`（`Link` と同じ）を持たせて書き戻す。
2. **共有・バックアップ JSON から取り込んだプロジェクトの `project.settings.json` に、`csv`（CSV の全文の写し）と `v` が書かれる**。`parseBackup` が JSON の枠のキーを「未知のキー」として設定に入れるため。CSV の本体（`project.csv`）は壊れないが、設定が大きくなり、古い写しが残る。

**要確認（分からない・確かめていない）**
3. **実際の JIRA（Cloud／Server）への取り込み**は、実機で確かめていない（6 章）。
4. **`Created`・`Updated`・`Sprint`・`Attachment`・`Outward issue link (Relates)` などの列があると、`check-jira` は「不明な列」として NG にする**（見本で確認。付録 E の「アプリ独自列」「標準列」にないため）。0.9.1 でアプリが `Created`/`Updated` を足すようになったので、**編集したプロジェクトは `check-jira` が NG になる**。JIRA の取り込みで無視されるのか・取り込まれるのかは未確認。アプリ独自列に足して `check-jira` を通すか、「JIRA用」の書き出しでは落とすかを決める必要がある（`golden` は変えない）。
5. **設定ファイルの形式の版番号**（`format`）は入れていない。方針は [spec-questions.md の B49](spec-questions.md)。
6. **読み取り専用で開く仕組みは、0.10.0 のロック（#62）で入った**が、未知の新しい形式を読んだときに読み取り専用で開く動作にはまだつながっていない（版番号 `format` を入れるときに結ぶ）。
7. **0.4.x 以前の見本は、その版のタグのコード（`core/src/project_io.cpp`）と CHANGELOG から再現したもの**で、当時の実ファイルではない。0.3.x の平置きは見本があるが、0.4.x のフォルダ構成の見本は 0.5.x の見本が兼ねる（0.4.x が書かなかった `weekly` を除いた形）。
8. **0.2.0 のタグのコードに `uiScale` などの prefs のキーがある**が、CHANGELOG は画面の拡大縮小を 0.3.0 としている。キーが入った版は 0.2.0 としたが、画面の操作が入った版との差は要確認。
9. **`ui.colW`・`ui.nameW` が入った版**は、JS 版の設定（SPEC 付録 B.1）から引き継いだもので、C++ 版では 0.1.0 から書いている。

## 6. JIRA 互換

JIRA の CSV を取り込める・「JIRA用」で書き出せることも、1.x の約束です。

**守り方（今）**
- `golden/*.roundtrip.csv`（アプリ用の書き出し）と `golden/*.jira.csv`（「JIRA用」の書き出し）と、**1 バイトも違わない**こと。`roadmap_golden_tests` と `cli_golden_*`（`rmcli` の出力との比較）が毎回確かめる。golden は元の実装が出力した正解で、更新するときは利用者に確認する。
- 「JIRA用」の書き出し: 階層を JIRA が扱える 3 段に畳む（SPEC 6.7）。計画の日付（`Start date`・`Due date`）を入れる。`rmcli import-export --format jira`、アプリの書き出しの「JIRAに取り込む用」。
- 書き出し前の検査 `jira_check`（`rmcli check-jira`。規則は付録 E）。アプリの画面からは呼んでいない（CLI のみ）。
- アプリが足す列（`Created`/`Updated` など）は **未知の列として往復**し、JIRA の標準の列と衝突しない見出しにする。値が 1 件もないプロジェクトでは列を作らない。
- 版ごとの見本（`tests/compat/`）は、「JIRA用」で書き出せて、書き出したものを再び取り込め、`check-jira` の問題が「不明な列」だけであることを確かめる。

**未確認（正直に）**
- **実際の JIRA への取り込みは、実機で確かめていない**（JIRA を使っていないため）。書き出しの形式は仕様どおりだが、実際の JIRA（Cloud／Server）で取り込めるかの確認は、必要になったときに行う。
- 上の 5 章の 4（未知の列と `check-jira`）。

## 8. 版ごとの見本とテスト

`tests/compat/` に、各版が書いた形の**架空の**プロジェクトを置いています（実データ・実在の名前は使いません。担当者は田中・佐藤・鈴木）。

| `v0.5/` | 0.5.x | フォルダ構成。`attachments`（`sha256` なし）・`weekly`・`ui.cols.pred`・`ui.dep` |
| `v0.7/` | 0.7.x | `ui.attachThumb`・`attachments[].sha256`（古い添付も混ぜる）。CSV に JIRA の日時の `Created`/`Updated` と `Sprint` |

各フォルダに `data/…`（プロジェクト）、`roadmap_prefs.json`、`share.json`（共有 JSON）があります。**その版が書かなかったキーは書いていません。** 設定・prefs・共有 JSON の形は、その版のタグのコードを見て揃え、今の版が書き直したときに**1 バイトも変わらない**ことで確かめています（バイト比較は設定 JSON と共有 JSON だけ。`roadmap_prefs.json` は、新しい版がキーを足す〔`newNameFormat`・`autoCompleteGitHub` など〕ので値の比較です）。CSV は、`csv.cpp` が 0.1.0 から変わっていないので、今の `rmcli import-export` で作りました。`.gitattributes` で `tests/compat/**` は改行を変換しません（CRLF を含めてバイトで比べるため）。

`tests/unit/test_compat.cpp` が確かめること:
1. 今の版でフォルダを開ける（警告なし・開いただけでは何も書かない・その版のキーが読める）。
2. 設定だけを保存し直しても CSV のバイト列が変わらず、控えも作らない。値を元に戻すと設定の JSON も元のバイト列。
3. 今の版が知らないキー（`futureKey`）が、2 章の表の「残る」場所で消えない。「消える」場所は `doctest::should_fail()` のテストで追跡している（直ると「失敗しなくなる」ので、`should_fail` を外して上のテストに足す）。
4. 見本の CSV（アプリの形式に正規化済み）を取り込んで書き出すと同じバイト列（設定を通る経路・全体の保存の経路でも）。書く前の CSV は控えに残る。任意の CSV のバイト保持を確かめるものではない（LF などは正規化される）。開いただけ・設定だけの保存で CSV に触れないことは 1・2 が確かめる。
5. 「JIRA用」で書き出せて、再び取り込め、`check-jira` の問題は「不明な列」だけ。
6. 共有・バックアップ JSON を読め、書き出し直すと同じバイト列。prefs は、その版が書いた値がすべて同じ値で残り、トップレベルの未知のキーが残る（新しい版が足すキーは増えるのでバイト比較はしない）。入れ子（`window`・`inherit`・テンプレートの項目）の未知のキーは `should_fail` で追跡。
7. 平置きをフォルダ構成へ移してもバイト列が変わらない。

実行: `ctest --preset linux-asan -R compat --output-on-failure`（または `roadmap_unit_tests "-tc=compat:*"`）。

## 9. 保存形式を変える PR のチェックリスト

CSV・フォルダ構成・`project.settings.json`・`roadmap_prefs.json`・共有／バックアップ JSON のどれかを変える PR は、本文に次を書きます。

- [ ] 変更の種類: 足すだけ／意味を変える／消す・名前を変える。**後ろ 2 つは 2.0 まで入れない**（やむを得ないなら 3 章の手順）
- [ ] 足すときは 4 章を守っている（既存の意味を変えない・読み飛ばせる・空なら書かない・足す場所）
- [ ] **見本を足した**: `tests/compat/v<版>/` を、直前の版のフォルダをコピーして作り、その版が書く形にした（その版が書かないキーは書かない）。`test_compat.cpp` の `kSamples` に行を足し、その版のキーが読めることの確認を足した
- [ ] 未知のキー: 新しい項目が未知のキーを保つ（`extra` など）。保てない場所に足していない
- [ ] golden が変わらない（変わるなら利用者に確認した）。`ctest -R golden` が通る
- [ ] **この文書（COMPAT.md）を更新した**: 7 章の表・2 章の表・5 章の「既知の穴」
- [ ] SPEC の付録 B（と 8 章）を更新した
- [ ] CHANGELOG の「互換」を、10 章の雛形で書いた
- [ ] 古い版で開いたとき（ダウングレード）に何が起きるかを書いた
- [ ] 実機（Windows・JIRA）で確かめていない点を、そのまま書いた

足さなくても CI が落ちる仕組みは作っていません。このチェックリストで守ります。

## 10. CHANGELOG の「互換」の書き方の雛形

各版の見出しの下に `### 互換` の節を作り、次の順で書きます（実例は 0.9.0）。該当しない行は省きます。

```markdown
### 互換
- <前の版> のデータは、そのまま使えます。<何をすると、どのファイルのどのキーが増える／変わる> （<空なら書かない、など>）
- <前の版> は <そのキー> を知らないので、<この版> で保存したデータを <前の版> で開いて保存し直すと、<未知のキーとして書き戻されます（消えません）／そのキーだけが消えます（ほかは残ります）>
- CSV: <変わらない（golden はそのまま一致）／末尾に <列> が増える（値が 1 件もないプロジェクトでは増えない）>
- 共有・バックアップの JSON: <入らない／入る>
- <自動の移行があるとき> 移行は自動では動かさない。<移行前の控えの場所>。<元に戻す手順>
- <この版では開けない古い版があるとき> <版> では開けません。<戻す手順>
- Windows の実機・JIRA の実機で確かめていないこと: <…>
```
