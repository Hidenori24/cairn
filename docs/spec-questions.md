判断を変える場合は、該当する SPEC の節に追記する。

として読めない・空・必須の項目がない）は古いロックとして扱い**、落ちない（読み取り専用で開き、引き継げる）。自分のロックを検査して「壊れている」と読めたときも、持ち主を失ったものとして保存せず、読み取り専用に切り替える（書き込み途中を読んだ偽陽性より、上書きを避ける方を選んだ）。**同期フォルダ（OneDrive・Google Drive など）は対象外**: 排他的な作成が保証されず、ロックのファイルが遅れて届くため。文書（SPEC 8.5.1・アプリの設定）に書いた。**平置きの旧形式にはロックを作らない**（プロジェクトのフォルダがない。フォルダ構成へ移したあと、開いているプロジェクトにロックを取る）。**まだ書いていない新しいプロジェクト**は、最初の保存のあとでロックを取る（それまでは誰も開けない）。**ロックを取る相手は開いているプロジェクトだけ**（一覧にある別のプロジェクトは取らない）。そのため、共有・バックアップ JSON の取り込みの「上書き」だけは、他の人の新しいロックがあるプロジェクトを上書きせず、別のプロジェクト「（読み込み）」として入れる。**引き継ぎ**: 確認ダイアログつき。新しい（古くない）ロックは「相手の未保存の変更は失われる」と出し、古い・解けている・壊れたロックは軽い確認（文言だけの違いで、手順は同じ）。引き継ぎは新しいトークンの上書きで、前の持ち主は次の保存の前の検査かハートビート（最長 30 秒）で気づく。同時に引き継いだ 2 人は、最後に書いた方のロックが残り、もう一方は書いたあとの読み直しか次のハートビートで気づく。起動直後に自分の前のアプリが落ちた跡のロック（同じ名前・同じマシン）も、3 分たつまでは他の人のロックと同じに扱い、自動では引き継がない（別のアプリが同じ名前で開いているかもしれないため）。**保存の前の検査で奪われたとき**: 保存せず（CSV・設定は 1 バイトも書かない）、読み取り専用に切り替え、**未保存の編集は別のプロジェクト「{名前}（未保存の編集）」として残して書く**（失わない。添付のメタ情報は複製しない）。元のプロジェクトはフォルダの版に読み直す。設定だけの未保存の変更（表示状態など）も同じ扱い（区別せず残す。まれな場面なので、取りこぼしより余計な 1 件を選んだ）。検査が「読めない」（ネットワークの不調）のときは、失ったとは決めず、保存を見合わせて今までの再試行（2→5→10 秒）に乗せる。**ロックが消されていた**ときも、失ったものとして扱う（Issue の文言どおり。自動では取り直さない。「再確認」で取り直せる）。**未保存の編集を失わない手段**は別プロジェクトとして残す方式にした（別名の CSV へ書き出す案は、読み取り専用のあいだに手元だけ編集する機能が要るので入れない。読み取り専用のあいだは、そもそも編集できない）。**フォルダのファイルが新しいとき**（ロックを知らない古い版・Excel が書いた）は、保存のたびに更新時刻を見て、書かずに外部変更の取り込み（8.5 の「両方変わっている」。フォルダの版を「（フォルダの版）」として残す）に回す（ロックの検査とは別の砦）。**読み取り専用の範囲**: 課題・設定（基準日・休業日・シナリオ・同時作業の制限・名前とキー）・添付・リンク・ベースライン・履歴/週のスナップショットの自動記録・週報の所感・置き換えの取り込み・削除・元に戻す、をすべて止める。表示の変更（ビュー・絞り込み・選択・折りたたみ・列幅・詳細パネル）は使えるが、ファイルへは書かない（メモリ上だけ）。書き出し（HTML・週次・CSV・JSON）・複製・新しいプロジェクト・「新しいプロジェクトとして取り込む」は使える（元のプロジェクトを変えないため）。止める場所は `Session`（`mutate` ほか）・`AppController` の入口・`Workspace::setFrozen`（書き込みの最後）の 3 重で、どれか 1 つが漏れても、ファイルへは書かない。**ログ**: ロックの内容（利用者名・マシン名）はログに出さない（画面と通知にだけ出す）。**ロックを使わない設定**は `useLock`（既定オン）。オフのあいだは作らず、見ない（他の人のロックがあっても編集できる。ひとりで使う・ロックが邪魔なとき）。**フォルダ監視**は Win32 を `FindFirstChangeNotification`（名前が分からない）から `ReadDirectoryChangesW`（名前が分かる）に替え、ロックのファイルだけの変更は無視する。通知があふれたとき（0 バイト）は、何が変わったか分からないので読み直す。Linux には監視がないので、コントローラ側では「ロックの更新で `mtime` が動かない・同期しても何も読み直さない」ことをテストした。**Windows 実機（共有ドライブ SMB の 2 台）での確認は未**（排他的な作成・同じ場所への上書きが他のマシンから読めること・強制終了のあとの引き継ぎ・`ReadDirectoryChangesW` の通知）。入れていない: ロックの自動の引き継ぎ（落ちた自分のアプリの跡）、ロック中の相手への通知（引き継がれた側は次の保存・ハートビートで気づく）、時計のずれの検出、複数のプロジェクトを同時にロックする機能、バックアップの zip を書く直前・設定を書く直前にも検査**し（`Workspace::setWriteGuard`）、引き継がれていれば残りを書かず読み取り専用に切り替える、(2) **書き終えたあとにも検査**し、引き継がれていたら「保存の途中で引き継がれました。混ざった可能性があるので内容を確かめてください」と知らせて読み取り専用にする、(3) 添付の本体を書く前・添付を外す前・プロジェクトを削除する前（`_削除済み` へ動かす前）にも、未保存の有無に関わらず検査する（`verifyLockBeforeWrite`）、(4) プロジェクトを切り替えるとき、前のプロジェクトを書けなかったら（引き継がれていた・確かめられない・書き込みの失敗）前のプロジェクトを書かず、未保存の編集を「（未保存の編集）」として残す、(5) JSON の取り込みの「上書き」は、開いていないプロジェクトのロックを**取って書き終えるまで持つ**（取れない・確かめられないときは上書きせず別のプロジェクトにする）。残る窓で起きること: ハートビートの更新と解放は、検査と書き込みの間に引き継がれると、相手のトークンを自分のもので上書き／相手のロックを消す。その場合も**相手のデータを上書きすることはなく**、相手（引き継いだ人）が次の検査（保存の前・ハートビート。最長 30 秒）でロックを失ったと気づいて、未保存の編集を別のプロジェクトとして残す（取りこぼしより、2 人が同時に編集権を持つ時間を短くする方を選んだ）。費用対効果から、サーバー側の排他（ファイルのバイト範囲ロック〔`LockFileEx`〕など）は入れていない（SMB の実装・同期フォルダで挙動が違い、実機で確かめられないため）。**Windows 実機で、上書き禁止の最後の砦として十分かの確認が要る** | 暫定 |

### C-3. 追加時の値の引き継ぎ（0.4.0。Issue #14）
- 引き継ぎの設定は prefs の `inherit`（`on` と項目ごとの真偽）。既定は `on=false` で今までどおり。項目が空の元からは写さず、通知にも出さない。
- 元は「同じ階層に追加」なら直前の兄弟（追加位置の直前の課題）、「子を追加」なら親。最上位を末尾に足すときは元がないので引き継がない。
- 種別は設定に関わらず階層で決める（Epic の子は Task、それ以外は Sub-task）。「種別」をオンにした兄弟からの引き継ぎだけ、兄弟の種別を写す。期間も兄弟からだけ（親の期間は子の合計で決まるため）。
- 期限は画面に出ている「その課題自身の期限」を写す。Deadline 列の無い CSV では Due date を写す。
- 担当者を引き継ぐと担当者ごとの負荷が偏る。今回は設定の説明に注意を書くだけで、負荷の通知は出さない（Issue の「検討」）。
